# Ingest Protocol v1

Date: 2026-06-18

Status: draft. This document defines the local and cloud wire contract used by extensions and apps to exchange records. It builds on the existing `record-store-v1` snapshot prototype, but it is not the same thing: snapshots describe a full store image; ingest batches describe changes a source wants another client to merge.

## 1. Goals

The protocol must support these flows with the same record shape:

- Mac Safari extension -> Mac App over App Group.
- Mac Chrome extension -> Mac App over localhost loopback.
- iOS Safari extension -> iOS App over App Group.
- App -> extension so annotation reflects learning state.
- Future App <-> cloud sync.

The protocol must not require:

- A plugin to install the learning app.
- The learning app to bundle a Safari extension.
- Cloud sync for same-device data exchange.
- A shared JS/Swift runtime library.

---

## 2. Terms

| Term | Meaning |
|---|---|
| `record` | One typed item from the record-store model, such as `lexicalItem`, `userLexicalState`, `exposureIndex`, `reviewLog`, or `settings`. |
| `recordId` | Canonical primary key: `type + ":" + encodeURIComponent(logicalId)`. All merge reads/writes use this, not raw `logicalId`. |
| `batch` | A transport envelope carrying records from one source to one receiver. |
| `cursor` | Opaque position in a sender or receiver change stream. Exact format is transport-owned. |
| `ack` | Receiver response that records whether a batch was accepted and which cursor to use next. |
| `source` | The client that produced the batch: Safari extension, Chrome extension, app, or cloud. |

## 3. Record Batch Shape

```json
{
  "protocolVersion": 1,
  "batchId": "bat_dev_chrome_mac_01_00000042",
  "sourceClientId": "dev_chrome_mac_01",
  "sourceKind": "chrome-extension",
  "targetKind": "mac-app",
  "direction": "push",
  "createdAt": "2026-06-18T10:00:00.000Z",
  "baseCursor": "opaque-source-cursor-before-this-batch",
  "records": [
    {
      "formatVersion": 1,
      "recordId": "exposureIndex:%E7%A2%BA%E8%AA%8D%3A%E3%81%8B%E3%81%8F%E3%81%AB%E3%82%93",
      "type": "exposureIndex",
      "domain": "exposureIndex",
      "logicalId": "確認:かくにん",
      "syncScope": "syncable",
      "mergeStrategy": "lww_pending_additive_exposure",
      "updatedAt": "2026-06-18T10:00:00.000Z",
      "deviceId": "dev_chrome_mac_01",
      "value": {
        "id": "確認:かくにん",
        "lexicalItemId": "確認:かくにん",
        "surface": "確認",
        "readingKana": "かくにん",
        "baseReadingKana": "かくにん",
        "seenCount": 1,
        "firstSeenAt": "2026-06-18T10:00:00.000Z",
        "lastSeenAt": "2026-06-18T10:00:00.000Z",
        "updatedAt": "2026-06-18T10:00:00.000Z",
        "deviceId": "dev_chrome_mac_01"
      }
    }
  ]
}
```

Required batch fields:

| Field | Rule |
|---|---|
| `protocolVersion` | Must be `1` for this draft. |
| `batchId` | Globally unique enough for idempotence. Re-sending the same batch must not duplicate append records. |
| `sourceClientId` | Stable per local install. Uses the existing `dev_...` convention where possible. |
| `sourceKind` | One of `safari-extension`, `chrome-extension`, `mac-app`, `ios-app`, `cloud`. |
| `targetKind` | One of `safari-extension`, `chrome-extension`, `mac-app`, `ios-app`, `cloud`. |
| `direction` | `push` or `pull_response`. Pull requests are transport-specific and may carry no records. |
| `createdAt` | ISO timestamp generated by the source. |
| `baseCursor` | Opaque cursor the source believes the receiver/sender last acknowledged; may be `null` for first exchange. |
| `records` | Array of records. Receivers must enforce count and byte limits. |

Recommended initial limits:

- Max records per batch: 1000.
- Max batch body: 1 MB for loopback/App Group, lower on iOS if needed.
- Max individual record value: 64 KB.

## 4. Ack Shape

```json
{
  "protocolVersion": 1,
  "batchId": "bat_dev_chrome_mac_01_00000042",
  "ok": true,
  "appliedRecordIds": [
    "exposureIndex:%E7%A2%BA%E8%AA%8D%3A%E3%81%8B%E3%81%8F%E3%81%AB%E3%82%93"
  ],
  "rejectedRecords": [],
  "receiverCursor": "opaque-mac-app-cursor-after-apply",
  "nextPullCursor": "opaque-source-cursor-to-request-next",
  "storageRevision": 43,
  "updatedAt": "2026-06-18T10:00:01.000Z"
}
```

Failure example:

```json
{
  "protocolVersion": 1,
  "batchId": "bat_dev_chrome_mac_01_00000042",
  "ok": false,
  "error": {
    "code": "invalid_record",
    "message": "recordId is not deterministic for type/logicalId"
  },
  "appliedRecordIds": [],
  "rejectedRecords": [
    {
      "recordId": "exposureIndex:not-canonical",
      "code": "invalid_record_id"
    }
  ]
}
```

Receivers should prefer all-or-nothing for a malformed batch. Partial accept is allowed only if the rejected records are independent and the ack lists them explicitly.

## 5. Merge Semantics

### 5.1 Global Rules

- Validate the batch envelope before reading records.
- Validate every record against the current record model.
- Verify `record.recordId === createRecordId(record.type, record.logicalId)`.
- Merge by `recordId`.
- Preserve unknown fields inside `record.value`.
- Treat tombstones (`deletedAt`) as records, not immediate deletion.
- Replaying the same batch must be idempotent.

### 5.2 Strategy Rules

| `mergeStrategy` | Initial behavior |
|---|---|
| `lww` | Later `max(updatedAt, deletedAt)` wins; tie-break by `deviceId`; preserve unknown fields from the winning record. |
| `append_lww_same_id` | Different `recordId`s coexist. Same `recordId` uses LWW. |
| `local_only` | Receiver keeps its local record; incoming local-only records from another client are rejected unless the receiver explicitly owns that singleton. |
| `server_authoritative` | Local receivers may store cached entitlements, but cloud/server records win when present. App-local StoreKit entitlement writes are authoritative only for that local platform. |
| `lww_pending_additive_exposure` | Temporary v1 behavior is LWW. Must be replaced by additive exposure deltas before cloud sync. Local same-device ingest may use it only with golden-vector coverage. |
| `additive_delta_pending` | Not accepted for final cloud sync until delta shape is defined. For local bridge v1, receiver may reject or treat as LWW with a warning. |

The pending strategies are intentionally explicit. Do not silently ship cross-device sync while any production record still depends on pending additive semantics.

## 6. Pull Model

Each transport may expose a different request shape, but the response is always a `recordBatch`.

Loopback example:

```http
GET /v1/records?since=opaque-cursor
Authorization: Bearer <pairing-token>
```

Response:

```json
{
  "protocolVersion": 1,
  "batchId": "bat_mac_app_00000112",
  "sourceClientId": "dev_mac_app_01",
  "sourceKind": "mac-app",
  "targetKind": "chrome-extension",
  "direction": "pull_response",
  "createdAt": "2026-06-18T10:05:00.000Z",
  "baseCursor": "opaque-cursor",
  "records": []
}
```

Minimum app -> extension records:

- `settings`, so extension annotation uses app-owned settings.
- `userLexicalState`, so known/forgot/ignored words render correctly.
- Optional `entitlements`, only if the extension still needs local paywall state during transition.

## 7. Transport Requirements

### 7.1 App Group

- Shared file/SQLite exchange must use atomic writes.
- Legacy `app-state-v1.json` remains readable during migration.
- Do not let a new record-store writer make old Safari content scripts corrupt data. Use a version gate or dual-write during transition.

### 7.2 Loopback

- Bind only to `127.0.0.1`, never `0.0.0.0`.
- Use a pairing token, not an unauthenticated port.
- Chrome discovers the server by probing a narrow port range.
- Every request validates token, method, path, protocol version, byte size, and record count.
- The Mac app must add `com.apple.security.network.server`.
- The extension must keep a durable local queue so app downtime never loses records.
- All loopback fetches run in the **background service worker** (which owns the one
  `MacLoopbackClient`); content scripts and the popup proxy to it via `BackgroundLoopbackClient`.
  A content-script fetch would carry the page Origin — the server applies it (token-gated) but
  echoes no `Access-Control-Allow-Origin`, so the page can't read the response and the batch
  never clears. The worker's fetch is a first-party extension request, so it reads the ack and
  drains the queue.

### 7.3 Cloud

- Cloud auth and entitlement checks wrap the same batch protocol.
- Server receipt/account entitlement gates only cloud transport.
- Devices that cannot sync must stay locally usable.

### 7.4 Loopback pairing and smoke test

Pairing UX (T077):

- The Mac App generates an 8-char Crockford code on first launch and persists it
  (`LoopbackPairing`); the code **is** the bearer token. The loopback port is never reachable
  without it.
- The App shows the code in Settings › Extensions (Copy / New Code), with the listening port and
  last-connected time.
- The Chrome popup has a Mac-app panel: paste the code → Connect. It probes for the server,
  confirms the code is accepted, and distinguishes "Mac app not found" from "Code rejected", then
  syncs the current state. Both sides normalize the code to `A-Z0-9` (case/space/dash tolerant).

Automated wire smoke test:

```bash
npm run test:loopback-smoke
```

This compiles the production `LoopbackRouter` / `HTTPRequest.parse` / `LoopbackResponse` /
`IngestProtocol` against a stub store and drives them over a real `127.0.0.1` TCP socket exactly as
the extension would: discovery, 401 without/with a wrong code, authorized ingest, and pull-back.
(The accept loop uses a plain POSIX socket because `NWListener` needs system networking services
unavailable in headless CI; the routing/auth/parsing under test are the production types.)

Manual browser-GUI smoke test (the half automation can't cover):

1. `npm run build:safari:mac` (or run the Mac App) so the loopback server is live; copy the
   pairing code from Settings › Extensions.
2. In Chrome, load `packages/extension` unpacked (chrome://extensions → Developer mode → Load
   unpacked).
3. Open the extension popup → Mac app panel → paste the code → Connect. Expect "Connected".
4. Browse a Japanese page so exposure is recorded, click Connect/Sync again, and confirm the words
   appear in the Mac App's Discover/Library (the App auto-refreshes every 2s).

## 8. Implementation Checklist

1. Add JS `createRecordBatch(records, options)`.
2. Add JS `validateRecordBatch(batch)`.
3. Add JS `mergeRecord(existing, incoming, strategy)`.
4. Add JS `ingestBatch(store, batch)`.
5. Add golden vectors for:
   - replaying the same batch,
   - Safari + Chrome same `recordId`,
   - same timestamp device tie-break,
   - append-only different ids,
   - tombstone vs active record,
   - invalid deterministic id rejection,
   - pending additive strategy behavior.
6. Port the same vectors to Swift before enabling Mac App ingest.
7. Add transport adapters only after the contract tests pass.
